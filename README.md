# Employment Management

Spring Boot CRUD practice application for managing employees through REST APIs and a professional web UI.

Employee records are persisted in PostgreSQL. The database is the source of truth: records survive application restarts.

## Architecture

```text
Employment Management UI/API
         |
         v
Spring Boot Application
         |
         v
    PostgreSQL
         |
         v
employee-managementdb
         |
         v
    employees table
```

- `controller` — HTTP mapping only (`/api/employees`)
- `service` — validation rules, duplicate-email checks, CRUD
- `repository` — Spring Data JPA access to PostgreSQL
- `model` — JPA `Employee` entity mapped to `employees`
- `exception` — not-found, duplicate email, validation, and database errors

Spring Boot serves both the frontend and the API from the same process:

- `/` → frontend
- `/api/employees` → REST API

PostgreSQL runs as a **separate** process or container. The application image does **not** include a PostgreSQL server.

## Environment variables

The datasource is built at runtime from environment variables. Do not bake credentials into the Docker image.

| Variable | Purpose | Learning-project example |
| --- | --- | --- |
| `POSTGRES_HOST` | PostgreSQL hostname | `postgres` in Kubernetes/Compose, or the host of your local instance |
| `POSTGRES_PORT` | PostgreSQL port | `5432` |
| `POSTGRES_DB` | Database name | `employee-managementdb` |
| `POSTGRES_USER` | Database user | `postgres` |
| `POSTGRES_PASSWORD` | Database password | `postgres` (development value only) |

`POSTGRES_PASSWORD=postgres` is the intentionally chosen **learning** password. Do not use it as a production secret.

See `.env.example` for a local Compose template.

## Database schema

Hibernate `ddl-auto=update` creates or updates the `employees` table on startup. It does **not** use `create-drop`, so existing rows are not destroyed.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `BIGSERIAL` / identity | Generated by PostgreSQL |
| `name` | `VARCHAR(100)` | Required |
| `occupation` | `VARCHAR(100)` | Required |
| `email` | `VARCHAR(255)` | Required, unique |
| `years_of_experience` | integer | Required, 0–80 |

## Employee CRUD flow

1. `POST /api/employees` — normalize input, reject duplicate email, `INSERT` into `employees`
2. `GET /api/employees` — `SELECT` all rows, ordered by `id`
3. `GET /api/employees/{id}` — `SELECT` by primary key, or 404
4. `PUT /api/employees/{id}` — update existing row, keep the same `id`
5. `DELETE /api/employees/{id}` — delete existing row, or 404

## Local PostgreSQL setup

Start PostgreSQL separately from the application (Compose, Docker, or an existing instance). Example with Compose:

```bash
docker compose up -d postgres
```

Or a standalone container:

```bash
docker run --name employment-management-postgres \
  -e POSTGRES_DB=employee-managementdb \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -p 5432:5432 \
  -d postgres:16-alpine
```

## PostgreSQL verification commands

```bash
psql -h "$POSTGRES_HOST" -p 5432 -U postgres -d employee-managementdb
```

Inside `psql`:

```sql
\dt
SELECT * FROM employees;
SELECT COUNT(*) FROM employees;
```

After an application restart, `GET /api/employees` and `SELECT * FROM employees` must still return the same rows.

## REST API

| Method | Path | Description | Success status |
| --- | --- | --- | --- |
| POST | `/api/employees` | Create employee | 201 Created |
| GET | `/api/employees` | List all employees | 200 OK |
| GET | `/api/employees/{id}` | Get employee by ID | 200 OK |
| PUT | `/api/employees/{id}` | Update existing employee | 200 OK |
| DELETE | `/api/employees/{id}` | Delete employee | 204 No Content |

The client must not provide `id` on POST. PostgreSQL assigns identity IDs. PUT never creates a new employee and never changes the ID.

### POST example

```http
POST /api/employees
Content-Type: application/json
```

```json
{
  "name": "Manjunath",
  "occupation": "Software Engineer",
  "email": "manjunath@example.com",
  "yearsOfExperience": 5
}
```

Missing employee `404`:

```json
{
  "message": "Employee with ID 10 not found"
}
```

Duplicate email `400`:

```json
{
  "message": "An employee with this email already exists"
}
```

If PostgreSQL is unreachable, the API returns HTTP 503 with a generic database-unavailable message. SQL details are not returned to clients.

## Validation rules

- Name, occupation, email, and years of experience are required
- Blank and whitespace-only values are rejected
- Email must be a valid address
- Years of experience cannot be negative and cannot exceed 80
- Name and occupation have a maximum length of 100 characters
- Duplicate emails are rejected on both POST and PUT
