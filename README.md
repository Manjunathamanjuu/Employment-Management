# Employment Management

Spring Boot CRUD practice application for managing employees through REST APIs and a professional web UI.

This project is intentionally simple: there is no database, no authentication, and no extra infrastructure. Employee records are stored in memory for the lifetime of the running process.

## Features

- Create, read, update, and delete employees
- Sequential unique IDs generated by the application
- Bean Validation for required fields, email format, and experience range
- Duplicate email prevention
- Centralized exception handling with clean JSON errors
- Professional responsive frontend
- Client-side search
- Dashboard statistics
- Automated JUnit and MockMvc tests
- Multi-stage Docker build with one final image and one Compose service

## Technology stack

- Java 17+
- Spring Boot 3.x
- Maven
- Spring Web
- Bean Validation
- JUnit and Spring Boot Test
- HTML5, CSS3, and vanilla JavaScript
- Docker and Docker Compose

## Architecture

The application uses a small layered design:

- `controller` — HTTP mapping only
- `service` — business rules and in-memory storage
- `model` — employee data
- `exception` — not-found, duplicate email, and global error handling

Spring Boot serves both the frontend and the API from the same process:

- `/` → frontend
- `/api/employees` → REST API

## In-memory storage

Employee data is stored in a thread-safe in-memory collection inside `EmployeeService`.

- Data exists while the application is running
- Data is lost when the application restarts
- There is no database configuration and no database dependency

This limitation is intentional for practice.

## REST API

| Method | Path | Description | Success status |
| --- | --- | --- | --- |
| POST | `/api/employees` | Create employee | 201 Created |
| GET | `/api/employees` | List all employees | 200 OK |
| GET | `/api/employees/{id}` | Get employee by ID | 200 OK |
| PUT | `/api/employees/{id}` | Update existing employee | 200 OK |
| DELETE | `/api/employees/{id}` | Delete employee | 204 No Content |

The client must not provide `id` on POST. The application assigns sequential IDs starting at 1. PUT never creates a new employee and never changes the ID.

### POST example

```http
POST /api/employees
Content-Type: application/json
```

```json
{
  "name": "Manjunath",
  "occupation": "Software Engineer",
  "email": "manjunath@example.com",
  "yearsOfExperience": 5
}
```

Response `201`:

```json
{
  "id": 1,
  "name": "Manjunath",
  "occupation": "Software Engineer",
  "email": "manjunath@example.com",
  "yearsOfExperience": 5
}
```

### GET all example

```http
GET /api/employees
```

Empty collection:

```json
[]
```

### GET by ID example

```http
GET /api/employees/1
```

Missing employee `404`:

```json
{
  "message": "Employee with ID 10 not found"
}
```

### PUT example

```http
PUT /api/employees/1
Content-Type: application/json
```

```json
{
  "name": "Manjunath Updated",
  "occupation": "Senior Software Engineer",
  "email": "manjunath.updated@example.com",
  "yearsOfExperience": 6
}
```

### DELETE example

```http
DELETE /api/employees/2
```

Successful delete returns no body and HTTP 204.

## Validation rules

- Name, occupation, email, and years of experience are required
- Blank and whitespace-only values are rejected
- Email must be a valid address
- Years of experience cannot be negative and cannot exceed 80
- Name and occupation have a maximum length of 100 characters
- Duplicate emails are rejected on both POST and PUT

Invalid requests return HTTP 400. Example duplicate email response:

```json
{
  "message": "An employee with this email already exists"
}
```

Unexpected failures return HTTP 500 with a generic message. Stack traces are never returned to the client.

## Multiple employee creation

Every POST creates a new employee. Existing records are never overwritten.

After ten POST requests, `GET /api/employees` returns all ten employees with unique IDs. The frontend supports the same behavior when employees are added one after another.

## Postman testing

Base URL: `http://localhost:8080/api/employees`

2. `GET /api/employees` and confirm 10 records

5. `GET /api/employees/1` and confirm the ID is still 1
6. `DELETE /api/employees/2`
7. `GET /api/employees/2` and expect 404
8. Validation tests: `{}`, missing fields, `email: "abc"`, `email: "not-an-email"`, `yearsOfExperience: -1`, `yearsOfExperience: "five"`, whitespace-only name, very long name
9. Duplicate email: POST the same email twice and expect 400
10. Invalid ID: `GET /api/employees/abc` and expect 400
11. Complete CRUD lifecycle: create, read, update, delete, then confirm GET all

  "email": "employee1@example.com",

## Docker

The project uses:

- One Dockerfile
- A multi-stage build (frontend prepare, Maven backend build, lightweight JRE runtime)
- One final image: `employment-management:latest`
- One Docker Compose service
- One container: `employment-management`

Frontend and backend are packaged together. Spring Boot serves both on port 8080. There is no Nginx and no second container.

### Docker commands

```bash
docker compose build
docker compose up -d
docker logs employment-management
docker compose down
```

Then open:

- Frontend: http://localhost:8080/
- API: http://localhost:8080/api/employees

In-memory data is lost when the container is recreated, which is expected.

## Important limitation

This application uses in-memory storage only. All data will be lost when the application restarts. This behavior is intentional for practice.
